# План плагина PHPStan Baseline Highlighter

## Цель первой версии

Плагин для IDE на IntelliJ Platform показывает маркеры в гутере возле объявлений классов и методов, связанных с записями PHPStan baseline. Подсказка объясняет исключение, по клику можно открыть соответствующую запись в baseline. Плагин работает локально и не запускает PHPStan, PHP, Composer или Docker.

Маркер означает наличие записи в baseline. Он не подтверждает, что нарушение существует в текущем коде: исключения могут устаревать. Номера строк нарушений стандартный baseline не хранит.

PHP-поддержка подключается опционально: JetBrains PHP (`com.jetbrains.php`) либо PHP for OpenIDE (`ru.openide.openphp`), включая Ракету. Общая часть не зависит от API поставщика. Без PHP-плагинов сохраняются индекс, настройки и список записей файла; маркеры объявлений требуют одного из поддерживаемых адаптеров. Поддержка остальных PHP-плагинов автоматически не предполагается.

## Границы MVP

Включить:

- Выбор baseline-файлов в настройках проекта; несколько файлов могут использоваться одновременно.
- Чтение стандартных NEON baseline с `parameters.ignoreErrors` и записями `message`, `path`, необязательными `identifier` и `count`.
- Маркеры у именованных классов, интерфейсов, трейтов, enum и объявленных в них методов, если удалось определить владельца записи.
- Подсказки с сообщениями, идентификаторами, количеством ожидаемых совпадений и источником.
- Переход к записи baseline; выбор из списка, когда записей несколько.
- Автоматическое обновление после изменения baseline или PHP-документа, включая несохранённые правки в редакторе.
- Действие «Показать записи baseline для текущего файла» для всех записей файла, в том числе без однозначной привязки к классу.
- Включение и отключение плагина на уровне проекта и стандартное управление видимостью gutter icons.

Оставить за пределами MVP:

- Запуск анализатора и подсветку точных строк нарушений.
- Проверку актуальности исключений, удаление записей и quick fixes.
- Маркеры возле свойств, отдельных выражений, анонимных классов и глобальных функций.
- Автоматический обход `includes` и выбор PHPStan-конфигураций; первоначально пользователь явно выбирает источники.
- Выполнение конфигураций на PHP, полную интерпретацию PHPStan-конфига, подстановки произвольных параметров и глобальные `ignoreErrors` без пути.
- Маски в `path`, массивы `paths`, `messages`, `rawMessage` и другие расширенные формы исключений.
- Интеграцию с CI, публикацию в Marketplace и поддержку Remote Development как обязательное условие первого выпуска.

Неподдерживаемые формы должны быть видны в диагностике источника. Нельзя молча интерпретировать их как обычную запись или показывать «исключений нет», когда источник прочитан не полностью.

## Исходные данные Ракеты

При подготовке плана в соседнем репозитории `../raketa` обнаружены 27 baseline-файлов: около 22 тысяч записей, примерно 7,6 МБ суммарно. Это размер всех найденных baseline, а не одного активного набора настроек.

В основном конфиге `app/raketa/code_quality/.phpstan.neon` подключено несколько baseline и отключена проверка неиспользуемых исключений: `reportUnmatchedIgnoredErrors: false`. Поэтому устаревшие записи — ожидаемый случай.

Плагин должен оставаться независимым от Ракеты. Её файлы используются как материал для проверки производительности и набора форм сообщений; пути и названия контекстов не зашиваются в код. В репозиторий плагина добавляются минимальные обезличенные примеры.

## Сравнение с PHPStan Toolbox

Проверен [PHPStan Toolbox](https://plugins.jetbrains.com/plugin/19791-phpstan-toolbox), исходники [shyim/idea-phpstan-toolbox](https://github.com/shyim/idea-phpstan-toolbox/tree/e2c2497b1cd5fea44eafbccecaaae6f0265804ea). Сравнение основано на коде ревизии `e2c2497b1cd5fea44eafbccecaaae6f0265804ea`; установка и проверка в работающей IDE не выполнялись.

| Возможность | PHPStan Toolbox по исходникам | Планируемый MVP |
|---|---|---|
| Источники | Индексирует файлы с точным именем `phpstan-baseline.neon` | Явно выбранные источники с любыми именами |
| Пути | Сопоставляет исходный `path` с путём PHP-файла относительно корня проекта | Нормализует путь относительно заданной базовой директории |
| Отображение | Inspection warning на именах классов с общим числом исключений файла | Отдельные gutter icons классов и методов |
| Содержание | Суммирует `count`; сообщения и идентификаторы в модель индекса не сохраняет | Хранит и показывает отдельные записи с владельцами |
| Несколько источников для файла | Inspection использует первый результат индекса | Показывает все выбранные источники |
| Навигация | Отдельного перехода к записи в проверенном коде нет | Переход к конкретной записи с актуализацией координат |
| Изменение baseline | Quick fix `Remove file from baseline` удаляет сохранённый диапазон строк | Только чтение и навигация |
| Запуск PHPStan | Проверенные компоненты работают через индекс IDE без анализатора | Аналогично, без внешних процессов |

Механизм индексации можно изучить в [PhpstanIgnoreIndex.kt](https://github.com/shyim/idea-phpstan-toolbox/blob/e2c2497b1cd5fea44eafbccecaaae6f0265804ea/src/main/kotlin/de/shyim/ideaphpstan/index/PhpstanIgnoreIndex.kt), поведение подсветки — в [ClassHasIgnoredErrors.kt](https://github.com/shyim/idea-phpstan-toolbox/blob/e2c2497b1cd5fea44eafbccecaaae6f0265804ea/src/main/kotlin/de/shyim/ideaphpstan/inspection/ClassHasIgnoredErrors.kt), изменение baseline — в [RemoveFileFromBaseLineIntention.kt](https://github.com/shyim/idea-phpstan-toolbox/blob/e2c2497b1cd5fea44eafbccecaaae6f0265804ea/src/main/kotlin/de/shyim/ideaphpstan/intention/RemoveFileFromBaseLineIntention.kt).

Для Ракеты готовая версия не закрывает требования: имена вроде `phpstan-baseline-architecture.neon` отфильтровываются, а пути вида `../raketa/...` не совпадают с путями относительно корня репозитория. Одного исправления имени baseline недостаточно: нужны изменение модели данных, вычисление путей и отдельный интерфейс маркеров/переходов.

На момент проверки Marketplace API возвращает последнюю версию `0.0.7` от 20 января 2024 года; последняя ревизия публичного репозитория также датирована этим днём. Отсутствие верхнего ограничения версии IDE в метаданных не подтверждает работу в современной PhpStorm. Файл лицензии в проверенном дереве репозитория не найден; возможность использования чужого кода необходимо выяснить до выбора форка или переноса реализации.

Решение: по указанию пользователя реализован собственный плагин. Toolbox использован только как технический ориентир; его исходники не перенесены.

## Состояние реализации

Реализован MVP 0.1.1: независимый Gradle/Kotlin-проект, ограниченный структурный NEON-парсер, индекс проекта, настройки источников и диагностика, маркеры классов/методов, подсказки, навигация и действие для файла. Индекс обновляется по document/VFS events с debounce и отменой устаревших разборов. Настройки локальны для workspace. Статусы источников и вычисленные пути показываются под таблицей настроек. PSI-интеграции вынесены в два опциональных адаптера через собственный extension point; изменение состава адаптеров инвалидирует кэш маркеров.

SDK сборки по умолчанию — PhpStorm 2025.2.6.2, JDK 21, диапазон совместимости ограничен ветками 252–263. В текущем окружении fixture-тесты выполняются на IDEA Ultimate 2025.2.6.2 с PHP-плагином. Совместимость с установленной PhpStorm 2026.3 проверяется Plugin Verifier отдельно.

Автоматизированы проверки ядра и IDE-интеграции для обоих PHP-плагинов, а также загрузки при отсутствии обоих. Дополнительно выполнен разбор всех 27 baseline Ракеты и замер привязки большого класса. Результаты и воспроизводимые команды — в `VALIDATION.md`; инструкция установки — в `README.md`.

Оставшиеся проверки перед расширением внутреннего использования: ручной просмотр редактора в светлой/тёмной теме, проверка смены ветки в большой открытой IDE, двух одновременно открытых проектов и полный профиль памяти/отзывчивости IDE. Отдельный JVM benchmark не заменяет эти проверки.

## Поведение в редакторе

Один значок на объявление. Если к нему относятся несколько записей, они объединяются в одну подсказку и список переходов. Выбрать различимый значок, подходящий для светлой и тёмной темы; значение не должно передаваться только цветом.

Маркер класса агрегирует записи этого класса, в том числе распределённые по его методам. Маркер метода содержит только записи, явно относящиеся к объявлению этого метода. В подсказке класса группировать записи по методам и отдельно показывать записи уровня класса/файла.

Пример подсказки:

```text
PHPStan baseline — 2 записи
Наличие нарушения в текущем коде не проверялось.

Method Example\OrderService::save() has no return type specified.
identifier: missingType.return
Ожидаемых совпадений: 1
Источник: phpstan-baseline.neon:18

Example\OrderService should not depend on Example\LegacyGateway
identifier: phpat.dependencies
Ожидаемых совпадений: 2
Источник: phpstan-baseline-architecture.neon:41
```

`count` — ожидаемое число совпадений при анализе, а не число строк, методов или уникальных записей. В UI различать число записей и это поле; отсутствие `count` не заменять придуманным значением.

Длинную подсказку ограничить несколькими записями с указанием общего количества. Полный список доступен по клику. Одинаковые сообщения из разных baseline сохраняют отдельные источники.

При единственной записи клик открывает baseline и выделяет её `message`. При нескольких — открывает список с сообщением и источником; выбор ведёт к нужной записи. Источник и координаты перед навигацией перепроверяются, чтобы изменения документа не привели к переходу в чужую запись.

Тексты интерфейса вынести в resource bundle. Для первого использования предусмотреть русскую локализацию.

## Правила привязки записей

Порядок: сначала совпадение пути файла, затем извлечение владельца из поддерживаемой формы сообщения, затем сопоставление с объявлениями в PHP PSI текущего файла. Поиск всех символов проекта и разрешение типов не требуются.

| Содержание сообщения | Куда привязывать |
|---|---|
| `Method Example\Service::save() has ...` | К объявлению `save` указанного класса и в сводку класса |
| `Return type of method Example\Service::save() ...` | Аналогично, после добавления отдельного распознавателя этой формы |
| Архитектурное `Example\Service should not depend on Example\Other` | К классу слева; зависимость справа не является владельцем записи |
| Сообщение о свойстве `Property Example\Service::$value ...` | К указанному классу; маркер свойства отложен |
| `Call to an undefined method Example\Other::run()` | Точный метод-владелец неизвестен; имя вызываемого метода нельзя использовать для маркера объявления |
| Общее `Unsafe usage of new static()` | Точный владелец неизвестен |

Для неизвестного владельца допустим маркер на единственном именованном типе файла, но запись должна быть явно обозначена как «запись файла, принадлежность классу не определена». Если типов несколько, такую запись показывать только через действие для файла.

Если сообщение явно называет класс, отсутствующий в текущем файле, не переносить запись на другой класс. Если класс найден, но названный метод отсутствует, показать запись в сводке этого класса с пояснением о ненайденном объявлении. Это также покрывает устаревшие имена и методы из трейтов/родителей без попытки их глобального разрешения.

Дополнительные правила:

- Сопоставлять полное имя класса, нормализуя начальный `\` и учитывая регистронезависимость имён классов и методов PHP.
- Отдельно поддержать `__construct`, несколько namespace и несколько типов в одном файле.
- Извлекать именно субъект диагностического сообщения. Наличие `Class::method()` в произвольном месте текста недостаточно.
- Распознаватели версионировать и покрывать примерами; новые формы сообщений добавлять независимо от UI.
- Произвольный regex из baseline не пытаться превращать в точную диагностику. Обрабатывать только понятные буквальные фрагменты поддерживаемых шаблонов; при неоднозначности оставлять привязку на уровне файла.
- Не применять PCRE из baseline как Java regex к PHP-коду: синтаксис отличается, а поиска по тексту недостаточно для определения владельца.

## Источники и настройки

В настройках проекта — таблица источников: включён/выключен, путь к baseline, базовая директория для относительных `path`, статус чтения. Выбранные пользователем файлы образуют активный набор; все найденные по имени baseline автоматически не подключаются.

Базовую директорию по умолчанию брать из каталога файла источника. Разрешить явное переопределение и показать несколько примеров вычисленных путей, чтобы пользователь мог проверить результат. Семантику относительных путей закрепить fixture-примерами с вложенными каталогами и included baseline на основе формата PHPStan.

Поддержать абсолютные и относительные пути, `..`, разделители Windows/Linux и платформенную чувствительность к регистру. Не требовать существования целевого PHP-файла при разборе: отсутствующий файл отображается в диагностике, а появление файла должно подхватываться без перенастройки источника.

Контейнерные абсолютные пути вроде `/web/...` в MVP не преобразовывать автоматически. В диагностике предлагать исправить источник/базовую директорию; явные таблицы отображения путей можно добавить следующим этапом.

Сохранять пути относительно корня проекта, когда это возможно. Личные абсолютные переопределения не навязывать командным настройкам. После открытия проекта индекс восстанавливается из настроек; отдельная база данных на диске в MVP не нужна.

## Технологии и архитектура

Kotlin, Gradle Kotlin DSL, IntelliJ Platform Gradle Plugin 2.x. Единственная обязательная runtime-зависимость — `com.intellij.modules.platform`. Адаптеры JetBrains PHP и PHP for OpenIDE регистрируются отдельными optional descriptors и реализуют `PhpDeclarationProvider`; общие маркеры получают только имена и platform PSI-идентификаторы. SDK обоих PHP-плагинов нужны при компиляции адаптеров, но не поставляются внутри ZIP. Целевые версии IDE и JDK фиксируются в сборке; совместимость с непроверенными версиями не обещается.

Компоненты:

1. `BaselineSettings` — выбранные источники и базовые директории.
2. `BaselineParser` — структура NEON, поля записей и диапазоны исходного текста.
3. `BaselinePathResolver` — нормализация путей и сопоставление с PHP-файлом.
4. `BaselineMessageClassifier` — безопасное распознавание владельца сообщения.
5. `BaselineIndexService` — сервис проекта с неизменяемым снимком индекса и его версией.
6. `PhpBaselineMatcher` — привязка записей к локальным объявлениям PHP PSI.
7. `BaselineLineMarkerProvider` — значки, подсказки и действия.
8. `BaselineNavigation` — актуализация координат и открытие источника.
9. `BaselineSourcesConfigurable` и действие для текущего файла — настройка и диагностика.

Минимальная запись индекса:

```text
BaselineEntry
  sourceUrl, sourceVersion, entryOffset, messageRange
  originalPath, normalizedTargetPath
  messagePattern, displayMessage, identifier?, count?
  ownerHint?: classFqn + methodName?
```

Индекс: `нормализованный путь PHP-файла → список BaselineEntry`. Для обновления дополнительно хранить записи по источнику. Кэш привязки: путь документа + modification stamp + версия снимка индекса. Не держать обычные PSI-объекты в долгоживущем индексе.

Маркеры привязывать к leaf-элементам имён объявлений через `LineMarkerProvider`. Его вызовы только читают готовый снимок/кэш: без чтения baseline с диска, рекурсивного обхода проекта и запуска фонового процесса на каждый PSI-элемент.

### Чтение NEON

Первый технический шаг — выбрать парсер с диапазонами исходного текста. Проверить доступные JVM-решения и их лицензию, поддержку NEON и работу без дополнительного установленного IDE-плагина.

Если подходящего решения нет, реализовать ограниченный структурный парсер формата генерируемого baseline. Явно описать поддерживаемую грамматику; не выдавать YAML-парсер за NEON и не строить разбор файла одним regex.

Обязательно корректно обработать табы/пробелы, комментарии, LF/CRLF, Unicode, одинарные/двойные кавычки, `#` внутри строк и двойной слой экранирования: сначала NEON, затем литералы в PCRE. Исходный regex сохранять независимо от удобного отображения. Ошибки разбора привязывать к файлу и диапазону.

### Обновление и потоки

- При старте проекта читать выбранные источники в фоне и публиковать готовый снимок атомарно.
- Слушать изменения документов и VFS только для настроенных источников; объединять серии событий с debounce ориентировочно 300–500 мс.
- Перечитывать изменённый источник, а не все baseline. Для большого файла предусмотреть отмену устаревшей задачи.
- Работать с текстом несохранённого документа, если он открыт в IDE, а не подменять его старым содержимым диска.
- Для PHP-документа пересчитывать только локальную привязку; сам индекс baseline от ввода PHP-кода не перестраивается.
- Доступ к PSI выполнять по правилам read actions; операции над текстом и индексом не держат длительный read lock. Учитывать закрытие проекта и невалидные файлы.
- После публикации снимка обновлять маркеры затронутых открытых PHP-файлов. Переименование/удаление источника и смена ветки не должны оставлять старые маркеры.
- При временно некорректном baseline удалить из актуального снимка записи этого источника и показать статус ошибки; не выдавать старые данные за текущие. Исправление автоматически восстанавливает маркеры.
- Во время индексации IDE не обращаться к глобальным PHP-индексам. Возможность работы в dumb mode подтвердить интеграционной проверкой перед объявлением поддержки.
- Экранировать сообщения в HTML-подсказках; текст baseline не интерпретируется как разметка.

## Производительность

Цель — влияние, незаметное при обычном редактировании. Следующие числа — стартовые бюджеты для проверки, а не результаты измерений:

- Фоновая загрузка примерно 22 тысяч записей из 8 МБ baseline — ориентир до 2 секунд на согласованной машине, без учёта общего старта IDE.
- Дополнительная удерживаемая память индекса и кэшей после GC — ориентир до 50 МБ на этом объёме.
- После прогрева получение и привязка записей обычного открытого файла — ориентир p95 до 10 мс; отдельно замерить файл с большим количеством методов/исключений.
- Плагин не добавляет длительные операции на EDT; отдельно проверять отзывчивость при первой загрузке и массовой смене файлов.
- В покое отсутствуют polling, фоновые процессы и повторяющиеся перестроения индекса.

Открытие PHP-файла без записей должно заканчиваться дешёвым поиском в индексе. Разбор всех baseline на каждый символ и компиляция всех regex на каждый маркер недопустимы.

Снять замеры на синтетическом наборе и локальных baseline Ракеты: время загрузки, память, время обновления одного источника, работа при вводе и смене ветки. Указать версии IDE/JDK, характеристики машины и методику, чтобы показатели можно было повторить. При превышении бюджета сначала профилировать, затем решать, нужен ли постоянный файловый индекс платформы.

## Проверки и критерии приёмки

Функциональные проверки:

- [ ] Метод-владелец получает маркер; метод, только упомянутый как вызываемый, его не получает.
- [ ] Архитектурная запись отображается у класса слева от `should not depend on`.
- [ ] Два класса в файле не получают чужие записи; неопределённая запись остаётся на уровне файла.
- [ ] Конструктор, интерфейс, трейт и enum работают по общим правилам; наследуемые методы не ищутся глобально.
- [ ] Неизвестная форма сообщения остаётся доступна в списке файла без придуманной точной привязки.
- [ ] Несколько baseline и одинаковые сообщения не теряют источники; `count` показывается отдельно.
- [ ] Вложенные относительные пути, абсолютные пути, пробелы и Unicode сохраняют корректное сопоставление.
- [ ] Ошибка или неподдерживаемая запись в источнике видна в диагностике.
- [ ] Навигация выделяет нужную запись после редактирования baseline, а не старый номер строки.
- [ ] Несохранённые изменения, удаление источника, смена активного набора и смена ветки обновляют маркеры.
- [ ] Проект с несколькими тысячами методов не тормозит при вводе; достигнуты либо обоснованно пересмотрены бюджеты производительности.
- [ ] Плагин работает без установленного PHPStan и PHP CLI и не создаёт внешние процессы.

Unit-тесты нужны для парсера, экранирования, путей и классификатора: здесь высок риск незаметного неправильного соответствия. Интеграционные fixture-тесты IDE — для PSI, навигации и инвалидирования. Визуальную часть проверить в sandbox; не заменять её только тестами модели.

MVP готов, когда выбранные baseline дают воспроизводимые маркеры классов и методов, по ним можно перейти к источнику, изменения корректно подхватываются, неоднозначность явно показана, а замеры подтверждают приемлемую нагрузку.

## Возможные следующие версии

В 0.1.15 добавлен разовый импорт baseline из выбранной PHPStan-конфигурации с обходом статических `includes`, отчётом проблем и добавлением новых строк до Apply. Изменения состава `includes` требуют повторного импорта; существующие источники сохраняются.

В 0.1.16 добавлены именованные профили наборов baseline с созданием, копированием, переименованием, удалением и выбором активного набора после Apply. Прежние источники автоматически переносятся в профиль по умолчанию. Индекс, маркеры, навигация и MCP учитывают активный набор; импорт ограничен выбранным профилем.

После пробного использования оценить потребность в постоянной синхронизации состава источников, маркерах свойств и отображении путей контейнера. Точные строки и подтверждение актуальности через PHPStan требуют отдельного согласованного этапа.
